1. VISÃO GERAL DE FUNCIONAMENTO DO SISTEMA
================================================================================
* O NutriFit deve funcionar como uma aplicação web com páginas Thymeleaf.
* O usuário acessa uma área pública para cadastro ou login.
* Depois do login, o sistema salva o objeto Usuario na sessão com o nome "usuarioLogado".
* Todas as telas privadas devem verificar se esse usuário está logado antes de listar, criar, editar, detalhar ou excluir dados.
* A regra principal do projeto é que cada informação pertence ao usuário logado.
* Portanto, refeições, planos alimentares, treinos, agendamentos e registros de hidratação não devem ser listados de forma global.
* Os services sempre recebem o Usuario logado e chamam repositories que filtram por esse usuário.

Fluxos Técnicos do Sistema:
* Cadastro: GET /cadastro exibe formulário. POST /cadastro salva Usuario validado. Após salvar, redireciona para /login ou já inicia sessão.
* Login: GET /login exibe formulário. POST /login chama AuthService.autenticar(email, senha). Se válido, salva usuarioLogado na HttpSession e redireciona para /dashboard.
* Dashboard: GET /dashboard chama DashboardService.montarResumo(usuarioLogado), reunindo contadores, próximo agendamento e hidratação do dia.
* CRUDs privados: Cada controller recupera usuarioLogado da sessão, chama o service correspondente e retorna templates Thymeleaf.
* Plano alimentar: Além dos próprios campos, o formulário carrega refeições do usuário para selecionar quais entram no plano.
* Hidratação: Permite registrar consumo diário. Um usuário não pode ter dois registros para a mesma data.
* Logout: GET /logout invalida a sessão e redireciona para /login.

================================================================================
Antes de implementar os fluxos, ajuste Usuario.java para não depender do controller ou service para preencher dataCadastro e ativo. Isso evita usuário salvo com campos nulos.
Localização: src/main/java/br/edu/nutrifit/model/Usuario.java
Ajuste: Importar jakarta.persistence.PrePersist, alterar dataCadastro para nullable=false/updatable=false, manter ativo nullable=false e criar o método prePersist().

Código:
@PrePersist
public void prePersist() {
    if (dataCadastro == null) {
        dataCadastro = LocalDateTime.now();
    }
    if (ativo == null) {
        ativo = true;
    }
}

7. CAMADA SERVICE
================================================================================
Os services concentram as regras de negócio. Controllers devem apenas receber a requisição, chamar o service e devolver o nome da view ou redirect.

UsuarioService.java (Dependência: UsuarioRepository)
- listarTodos(): Retorna todos os usuários (se a tela administrativa for usada).
- buscarPorId(Long id): Busca usuário por id ou lança exceção simples se não encontrar.
- buscarPorEmail(String email): Usado pelo AuthService.
- cadastrar(Usuario usuario): Valida e-mail duplicado, garante ativo=true e salva.
- atualizar(Usuario usuario): Valida e-mail duplicado ignorando o próprio id e salva alterações.
- desativar(Long id): Define ativo=false, em vez de excluir fisicamente usuário com dados vinculados.
- validarEmailDisponivel(Usuario usuario): Método privado para centralizar a regra de e-mail único.

AuthService.java (Dependência: UsuarioService ou UsuarioRepository)
- autenticar(String email, String senha): Busca usuário ativo por e-mail e compara senha (texto puro no MVP).
- usuarioPodeLogar(Usuario usuario): Confere se usuário existe e está ativo.
- validarSenha(String senhaDigitada, String senhaSalva): Isola a comparação de senha para facilitar hash depois.

DashboardService.java (Dependências: RefeicaoRepository, PlanoAlimentarRepository, TreinoRepository, AgendamentoRepository, HidratacaoRepository)
- montarResumo(Usuario usuario): Monta DashboardResumoDTO com dados do usuário logado.
- buscarProximoAgendamento(Usuario usuario): Busca próximo agendamento AGENDADO com data/hora futura.
- buscarHidratacaoHoje(Usuario usuario): Busca registro de hidratação da data atual.

RefeicaoService.java (Dependência: RefeicaoRepository)
- listarPorUsuario(Usuario usuario): Lista somente refeições do usuário logado.
- buscarPorIdEUsuario(Long id, Usuario usuario): Busca refeição apenas se pertencer ao usuário.
- salvar(Refeicao refeicao, Usuario usuario): Define o usuário logado na refeição e salva.
- excluir(Long id, Usuario usuario): Busca por id e usuário; exclui somente se pertencer ao usuário.
- calcularTotalCalorias(List<Refeicao> refeicoes): Soma calorias para detalhes de plano ou dashboard.

PlanoAlimentarService.java (Dependências: PlanoAlimentarRepository, RefeicaoRepository)
- listarPorUsuario(Usuario usuario): Lista planos do usuário logado.
- buscarPorIdEUsuario(Long id, Usuario usuario): Busca plano apenas se pertencer ao usuário.
- salvar(PlanoAlimentar plano, Usuario usuario, List<Long> refeicoesIds): Define usuário, valida datas, carrega refeições do próprio usuário e salva.
- excluir(Long id, Usuario usuario): Exclui plano do usuário logado.
- validarDatas(PlanoAlimentar plano): Impede dataFim anterior à dataInicio.
- carregarRefeicoesDoUsuario(List<Long> ids, Usuario usuario): Garante que o plano não receba refeições de outro usuário.

TreinoService.java (Dependência: TreinoRepository)
- listarPorUsuario(Usuario usuario): Lista treinos do usuário logado.
- buscarPorIdEUsuario(Long id, Usuario usuario): Busca treino apenas se pertencer ao usuário.
- salvar(Treino treino, Usuario usuario): Define usuário e salva.
- excluir(Long id, Usuario usuario): Exclui treino do usuário.
- validarTreino(Treino treino): Regra opcional para validar duração e frequência além das anotações.

AgendamentoService.java (Dependência: AgendamentoRepository)
- listarPorUsuario(Usuario usuario): Lista agendamentos do usuário logado.
- buscarPorIdEUsuario(Long id, Usuario usuario): Busca agendamento apenas se pertencer ao usuário.
- salvar(Agendamento agendamento, Usuario usuario): Define usuário, define status padrão se vazio, valida data futura e salva.
- excluir(Long id, Usuario usuario): Exclui agendamento do usuário.
- cancelar(Long id, Usuario usuario): Altera status para CANCELADO.
- concluir(Long id, Usuario usuario): Altera status para CONCLUIDO.
- validarDataFutura(Agendamento agendamento): Impede criação de novo agendamento no passado.

HidratacaoService.java (Dependência: HidratacaoRepository)
- listarPorUsuario(Usuario usuario): Lista histórico de hidratação.
- buscarPorIdEUsuario(Long id, Usuario usuario): Busca hidratação apenas se pertencer ao usuário.
- buscarPorData(Usuario usuario, LocalDate data): Busca registro de uma data específica.
- buscarHoje(Usuario usuario): Busca registro da data atual.
- salvar(Hidratacao hidratacao, Usuario usuario): Define usuário e valida duplicidade usuario+data.
- registrarConsumoHoje(Usuario usuario, Integer consumidoMl, Integer metaMl): Cria ou atualiza o registro do dia.
- excluir(Long id, Usuario usuario): Exclui registro do usuário.
- validarRegistroUnicoPorData(Hidratacao hidratacao, Usuario usuario): Impede duplicidade de hidratação na mesma data.

11. VALIDAÇÕES E REGRAS DE NEGÓCIO
================================================================================

* Treino: Na model (nome, tipo, nível, duração e frequência semanal válidos).
* Agendamento: No Service (bloquear criação de novos agendamentos no passado; status inicial padrão AGENDADO).
* Hidratacao: No Service / Banco (combinação usuario + data deve ser única; valores de consumo e metas dentro dos limites informados).
* Telas (HTML): Atributos required, minlength, maxlength, min, max, tipos corretos de inputs.

12. CONTROLE DE SESSÃO MANUAL (SEM SPRING SECURITY)
================================================================================
Para manter o MVP enxuto, utiliza-se HttpSession. Após autenticar com sucesso, salve o usuário na sessão:
session.setAttribute("usuarioLogado", usuario);

Em cada controller privado, recupere e valide obrigatoriamente a sessão ativa:
Usuario usuarioLogado = (Usuario) session.getAttribute("usuarioLogado");
if (usuarioLogado == null) {
    return "redirect:/login";
}

Regra Crucial de Segurança: Nunca busque, edite ou exclua registros utilizando apenas o id da entidade de forma isolada. Use sempre consultas compostas filtrando pelo usuário da sessão (ex: buscarPorIdEUsuario(id, usuarioLogado)).
